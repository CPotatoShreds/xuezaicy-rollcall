## 1. 背景与目的

申请人已完成对该校扫码签到模块的纯被动安全评估（评估对象：`identity.tc.cqupt.edu.cn` / `lms.tc.cqupt.edu.cn`，Tronclass 平台；方法：仅分析本人账号产生的流量，未向生产环境发起任何验证性请求）。报告得出四项发现：

1. **F1** 全部 API 走明文 HTTP（高危）；
2. **F2** 会话凭据为"静态核心 + 动态包装"结构，约 24 小时滚动续期，长效可重放（高危）；
3. **F3** 无任何客户端完整性校验（中危）；
4. **F4** 签到凭据可即时跨账号转递，二维码架构无法证明物理在场（中危，架构性）。

其中多项关键问题（会话失效策略、令牌校验逻辑、其他点名类型安全性、角色权限边界）**无法通过客户端流量判定**，需校方/厂商在服务端核实，或由申请人获得书面授权后以校方签发的测试账号在受控环境验证。

另，公开渠道已有针对同一厂商 Tronclass 平台（其他高校租户）的系统性安全研究，披露了若干**平台级问题**（详见第 3 节 A3）。该平台各租户同构、API 一致，建议一并核实本租户是否受影响。

**目的**：将附件报告第 7 节"待授权验证项"落实为逐项结论，为校方与厂商的整改提供可处置依据。

## 2. 申请事项

1. **第一优先**：请信息化办/厂商按第 3 节 A 部分清单，在服务端配置与日志中直接核实——无需任何主动测试，风险为零；
2. 对 A 部分无法覆盖的问题（B 部分清单），申请书面授权：由校方签发测试账号、约定测试范围与时间窗，由申请人按第 4 节方案执行受控验证。

## 3. 核查与验证清单

### A 部分：服务端直接核实项（建议优先，无需测试）

#### A1 会话管理（对应报告 F2）

| # | 核查项 | 期望的安全行为 |
|---|---|---|
| A1-1 | 会话重签发新值后，旧 `x-session-id` 是否即时失效 | 旧值下次请求应返回 401 |
| A1-2 | 服务端是否校验会话 ID 中间段（过期时间戳、随机段），还是仅识别 UUID + 用户 ID | 篡改任一段应失效 |
| A1-3 | 是否设置会话绝对有效期上限（非无限滚动续期） | 有硬上限 |

#### A2 签到 `data` 令牌（对应报告 F4）

| # | 核查项 | 期望的安全行为 |
|---|---|---|
| A2-1 | 令牌是否单次消费 | 同一 `data` 第二次提交应拒绝 |
| A2-2 | 时间窗宽度 | 建议 15–30 秒并高频轮换二维码 |
| A2-3 | 令牌是否绑定学号 / 课程 / 点名场次 | 应绑定。**平台公开研究显示 `data` 仅绑定"时间 + 全局密钥"：同一时刻的有效 `data` 在其他课程、甚至其他高校租户提交均被接受（多租户实测）。请重点核实本租户是否同样不绑定。** |
| A2-4 | `data` 生成密钥的存放与轮换策略 | 密钥仅存服务端、定期轮换（平台研究确认密钥不在任何客户端或学生可读接口中，属正面发现） |

#### A3 其他点名类型开通与安全性（平台情报，建议自查）

平台公开研究在其他 Tronclass 高校租户实测确认的问题，建议核实本租户是否开通相关类型并受影响：

| # | 点名类型 | 平台已证实的问题 | 本租户核查点 |
|---|---|---|---|
| A3-1 | 数字点名 | **学生可调用的点名详情接口直接返回正确点名码**（无需爆破，四位码亦可离线穷举） | 是否开通；接口是否向学生返回码值 |
| A3-2 | 雷达点名 | **提交空答案（不带坐标）即被判到场**，实测通过率 100% | 是否开通；空答案是否被拒 |
| A3-3 | 自主报到 | 空 PUT 即完成签到 | 是否开通；是否需要附加校验 |
| A3-4 | QR 点名（本报告主对象） | 多数租户的**教师端读取 `data` 接口对学生角色正确返回 403**、WebSocket 不推送 `data`（属正面发现） | 确认本租户教师接口角色校验同样严格；确认无任何学生可达接口泄漏进行中点名的 `data` |

#### A4 风控与日志（对应报告第 7.4 条）

- 是否具备关联查询能力：令牌 ID × 学号 × deviceId × 源 IP × 时间戳；
- 是否配置规则：同令牌多账号提交、同 deviceId 关联多账号、签到源 IP 不在校园网段、提交时序机器模式（毫秒级精确、固定间隔）。

#### A5 提权面

- 课程角色变更、邀请类接口对本租户学生角色的实际权限边界（平台研究：厂商已用 WAF 规则拦截公开提权路径，改角色接口对学生返回 403——请确认本租户一致，并保持监控）。

### B 部分：需授权测试账号的受控验证项

以下问题无法由配置检查或他租户结论替代，需在本租户用测试账号实测：

| # | 验证项 | 方法 | 账号需求 |
|---|---|---|---|
| B1 | 会话实际可重放窗口 | 测试账号登录 → 服务端重签 → 立即用旧值发请求，记录新旧值共存时长 | 学生 ×1 |
| B2 | 教师接口角色校验实测 | 学生会话访问只读管理类接口，确认返回 403（**仅访问确认，不尝试提权、不修改任何数据**） | 学生 ×1 |
| B3 | 令牌转递实测 | 测试课程内由教师账号发起点名，`data` 交第二测试账号在授权环境提交，记录实际成功率与有效时间窗 | 学生 ×2、教师 ×1 |
| B4 | 令牌单次消费与重放 | 同一 `data` 重复提交、延迟提交，验证 A2-1/A2-2 | 同 B3 |

## 4. 测试方案与交战规则（ROE）

- **范围**：仅限校方指定的测试课程与测试点名；不接触任何真实课程、真实学生数据；
- **账号**：仅使用校方签发的测试账号；**不以个人实名账号发起任何验证性请求**；不注册真实学号；
- **时间窗**：【建议约定在工作日晚间/周末，由信息化办指定】；
- **方法约束**：
  - 仅双账号对照与定点验证；不做端口扫描、目录爆破、大规模枚举；
  - 不做任何拒绝服务类测试；请求并发 ≤ 1；
  - 不尝试提权、不修改任何数据；A3 类问题仅以"发起测试点名 → 观察结果"方式验证；
  - 发现高危可利用问题立即停止测试并通报校方，不扩大范围、不留存利用代码；
- **留痕**：全程抓包留存，测试结束后完整操作日志随报告提交信息化办；
- **数据处置**：测试产生的令牌、会话、报文仅用于本报告；报告不含可直接利用的攻击实现；原始数据按校方要求销毁。
