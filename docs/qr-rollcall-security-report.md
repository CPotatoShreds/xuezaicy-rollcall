# 学在重邮（Tronclass）二维码签到机制安全评估报告

| 项目 | 内容 |
|---|---|
| 评估对象 | `identity.tc.cqupt.edu.cn` / `lms.tc.cqupt.edu.cn`（Tronclass 平台）扫码签到模块及相关会话机制 |
| 评估方法 | **纯被动分析**：对本人账号一次扫码签到产生的 HAR 流量（2026-09-18）做协议还原与本地离线检验 |
| 主动测试 | **无**。未向生产环境发起任何验证性请求，未接触任何第三方账号凭据 |
| 报告日期 | 2026-09-20 |
| 状态 | 初版，待校方/厂商复核 |

> 本报告全部结论基于提交人本人账号、本人设备产生的流量。所有令牌、会话标识、设备标识均已脱敏。

---

## 1. 摘要

对扫码签到流程的还原与离线分析得出四项主要发现：

1. **全部 API 走明文 HTTP**（高危）：会话凭据、JWT、签到请求均未加密传输，且因此不存在 TLS 指纹等常见自动化检测点。
2. **会话凭据为"静态核心 + 动态包装"结构，长效可重放**（高危）：识别身份的是整个登录期内不变的会话 UUID 与明文用户 ID，动态部分仅承担过期管理（约 24 小时滚动续期）。
3. **无任何客户端完整性校验**（中危）：请求中所有区分客户端类型的字段均为自报字符串，无法识别非官方客户端的提交。
4. **二维码签到在架构上无法证明物理在场**（中危，架构性）：签到凭据可即时跨账号转递；但凭据熵充足，**离线伪造不可行**（正面发现）。

其中 1 + 2 叠加构成完整的凭据窃取风险链；3 + 4 叠加构成代签风险链。修复建议见第 6 节。

---

## 2. 评估范围与方法

- 数据来源：提交人于 2026-09-18 17:11（UTC+8）通过企业微信进入"学在重邮"完成一次扫码签到时抓取的 HAR 文件（77 条记录，含 2 条 WebSocket）。
- 分析手段：请求/响应结构还原、字段逐字符比对、令牌结构与熵估计、针对令牌尾段的弱哈希假设本地穷举验证（md5/sha1/sha256 × 时间戳/课程 ID 组合）。
- 明确排除的手段：对生产环境的主动重放、令牌枚举、对他人流量的任何采集。报告中"待授权验证项"（第 7 节）仅建议由系统所有方在自有环境内核查。

## 3. 流程还原

### 3.1 登录链路

企业微信 → Keycloak（`/auth/realms/cqupt/broker/wechat-work/endpoint/...`）→ 换取会话。后续 API 认证**完全依赖自定义请求头 `x-session-id`**：抓取的 77 条请求中 0 条携带 Cookie 头（尽管服务端每个响应都在 `set-cookie`）。

### 3.2 扫码签到

```
PUT http://identity.tc.cqupt.edu.cn/api/rollcall/{rollcall_id}/answer_qr_rollcall
Content-Type: application/json
x-session-id: <会话凭据>

{"data":"<13位毫秒时间戳><29位十六进制>","deviceId":"<客户端自生成 UUIDv4>"}

→ 200 {"id":null,"status":"on_call"}
```

- `data` 即二维码内容中的签到凭据，总长 42 字符；前 13 位为毫秒时间戳，与扫码时刻吻合（距提交约 3 秒）；
- 无请求签名、无时间戳 HMAC、无定位字段、无任何附加校验字段；
- 教师端通知经 WebSocket（`/ntf/pubsub/{uid}`，事件类型含 `rollcall_alert`）。

### 3.3 会话凭据结构

对一次会话内 8 个不同 `x-session-id` 取值做逐字符比对，结构为：

```
V2-1-<会话UUID>.<base64(用户ID)>.<过期时间戳_ms>.<8位随机段>
```

| 分段 | 动态性 | 说明 |
|---|---|---|
| 会话 UUID | 静态 | 整个登录期不变，服务端识别身份的锚点 |
| base64(用户ID) | 静态 | 明文可读可改（如 `MjUyODk1` → `2528**`） |
| 过期时间戳 | 服务端控制 | 观察到至少 5 个不同取值逐次后延，约 +24h，属**滚动续期** |
| 8 位随机段 | 服务端重签时更换 | 非每请求轮换：同一取值最多被连续 7 个请求复用 |

另：`role_token` 为未签名的 base64 JSON（`{"exp":...` 开头），内容可读可改；`/api/jwt` 每次调用现签新 JWT，但仅用于统计上报，不承载关键操作。

## 4. 发现明细

### F1 API 明文 HTTP 传输 —— 高危

**现象**：`identity.tc.cqupt.edu.cn` 与 `lms.tc.cqupt.edu.cn` 的全部 API 请求及 WebSocket 均为 `http://` 明文。

**影响**：
- `x-session-id`、JWT、签到凭据明文过网，同一网段（教室/图书馆 Wi-Fi）的观察者可截获；
- 因无 TLS，**TLS 指纹（JA3/JA4）类自动化客户端检测天然不存在**；
- 任意中间位置可读取并重放请求。

**建议**：全站 HTTPS 并启用 HSTS；会话凭据停止经明文信道传输。

### F2 会话凭据长效可重放 —— 高危

**现象**：见 3.3。身份锚点（会话 UUID + 用户 ID）全期静态；动态部分仅服务过期管理；有效期约 24 小时且滚动续期。

**影响**：凭据一旦被截获（结合 F1 门槛极低），在最长约 24 小时窗口内可自任意网络位置、任意客户端重放，等同账号完全接管（含签到、作业、成绩查看等全部 API 权限）。

**建议**：
- 会话轮换时旧值**即时失效**（本轮抓包显示服务端多次重签，旧值是否失效无法由客户端流量判定，见第 7 节）；
- 设置绝对有效期上限，滚动续期不无限延长；
- 会话票据改为服务端签名（现 `role_token` 为未签名 JSON），并对用户 ID 段做防篡改保护。

### F3 无客户端完整性校验 —— 中危

**现象**：请求中区分客户端类型的字段全部为自报明文字符串：`User-Agent`（移动 WebView UA）、`Origin`/`Referer`（`http://mobile.tc.cqupt.edu.cn`）、`X-Requested-With`（被前端库覆盖为 `XMLHttpRequest`，标准安卓 WebView 应为宿主包名）、统计接口 body 内 `is_mobile:true`。客户端实质为 H5 页面，无原生层，亦无设备指纹、请求签名或 attestation 凭证。

**影响**：服务端无法从单个请求识别非官方客户端提交；叠加 F1（无 TLS 指纹）后，协议层对自动化提交完全无感知。

**建议**：放弃"识别客户端类型"思路，转向行为风控（见 F4 建议）与传输层加固。

### F4 二维码签到凭据可即时转递（架构性） —— 中危

**现象**：签到凭据 `data` 为独立字符串，提交接口无状态。凭据结构 `<毫秒时间戳><29 hex>` 中，时间戳仅表明服务端可能有时间窗校验，而转递是即时的，时间窗对转递无效。

**正面发现**：尾段约 116 bit 熵；对常见弱派生（时间戳及其与课程 ID 拼接的 md5/sha1/sha256 组合）的本地穷举均不匹配，剩余可能为服务端随机 nonce 或带密钥 HMAC——**离线伪造不可行**，令牌设计本身合格。

**影响**：教室内的到场者可将凭据实时转交场外账号完成签到；这是二维码作为可复制信道的固有局限，任何令牌层修复均无法根除。

**建议**：
- 服务端强制 `data` 令牌**单次消费 / 绑定单个学号**，有效期压缩至 15–30 秒并高频轮换二维码；
- 行为风控：同一令牌短时多账号提交、同一 deviceId 关联多账号、签到源 IP 不在校园网段、提交时序机器模式（毫秒级精确、固定间隔）；
- `deviceId` 当前为客户端自报 UUIDv4，建议改为服务端下发或绑定企业微信身份；
- 承认协议修复的天花板：如需强在场证明，考虑定位/校园网校验、随机口令、随机时点自拍或教师抽查等补充手段。

## 5. 风险链综合

- **凭据窃取链**：F1（明文传输）→ F2（长效静态凭据、无绑定、无校验）→ 账号完全接管。
- **代签链**：F4（凭据可即时转递）+ F3/F1（自动化提交无技术阻碍）→ 到场者可批量代签场外账号。
- **风险定性**：可被普通学生在无任何专业工具的情况下利用，利用成本极低、影响面为全校课程考勤与个人账号数据。

## 6. 修复优先级

| 优先级 | 措施 | 对应发现 |
|---|---|---|
| P0 | 全站 HTTPS + HSTS | F1 |
| P0 | 会话轮换旧值即时失效、设绝对有效期上限、会话票据服务端签名 | F2 |
| P1 | 签到令牌单次消费、绑定单学号、15–30s 有效期 | F4 |
| P1 | 行为风控规则（多账号同令牌/同设备、网段校验、时序检测） | F3、F4 |
| P2 | deviceId 服务端下发或企微身份绑定 | F4 |
| P2 | 在场证明类补充手段评估（定位/口令/抽查） | F4（架构性） |

## 7. 待授权验证项（建议由系统所有方在自有环境内核查）

以下问题无法由客户端流量被动判定，建议信息化办/厂商在服务端日志与配置中直接核实：

1. 会话重签新值后，旧 `x-session-id` 是否立即失效（决定 F2 的实际可重放窗口）；
2. 服务端是否校验会话 ID 中的过期时间戳与 8 位随机段，还是仅认 UUID + 用户 ID（决定该字段中间段可否被篡改）；
3. 签到 `data` 令牌是否单次消费、是否校验时间窗、是否绑定学号（决定 F4 转递的实际成功率）;
4. 现有日志是否记录足以支撑 F4 风控规则的字段（令牌 ID、学号、deviceId、源 IP、时间戳的关联查询）。
